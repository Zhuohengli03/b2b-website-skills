# 出海 B2B 建站 · 岗位 Agent 流水线总览

每个岗位一个 skill，每个 skill 未来对应一个独立 agent。agent 之间只通过文件交接（不通过口头转述），每个 skill 末尾的「流水线接口」写明了输入文件、输出文件、完成判定和回流规则。

## 岗位与 skill 对照

| 顺序 | 岗位 | skill | 核心产出 |
|---|---|---|---|
| 0 | 项目经理 / 需求采集 | `b2b-project-manager` | 需求单、素材清单、排期、任务分派；末尾验收单、资产清单（文件名仍叫交付清单）、后台手册 |
| 1 | 市场与竞品研究员 | `b2b-market-research` | 研究简报、关键词表 |
| 2 | 产品经理 / 策划 | `b2b-site-diagnosis` | 方案（建站诊断与方案建议）、站点地图与线框、技术清单、风格与字体方向 |
| 3 | 英文文案 | `b2b-copywriter` | 文案稿、事实来源表、标题与描述表 |
| 4 | 页面 / UI 设计师 | `b2b-ui-designer` | 设计稿、视觉系统、组件规范、响应式规则、设计决策说明 |
| 5 | 前端开发 | `b2b-frontend-dev` | 测试站、字段与区块说明、性能报告、前端自查表 |
| 6 | 后端 / 运维 | `b2b-backend-dev` | 询盘链路配置记录、CMS 字段与导入模板、多语言配置、基础设施清单、上线检查表 |
| 7 | SEO / GEO 专员 | `b2b-seo-specialist` | SEO 检查表、关键词落位表、Schema 验证、分析配置、内容计划、月报模板 |
| 8 | 测试 / QA | `b2b-qa-tester` | 测试报告、测试清单、复测记录、验收单草稿 |
| 9 | 上线后增长运营 | `b2b-growth-cs` | 询盘台账、月报、内容发布记录、外部提及记录 |

## 谁来跑这条流水线

`b2b-run` 是执行器，不是岗位：它自己不生产任何东西，只做四件事——建项目目录、按顺序调用上面十个 SKILL.md、检查每次交接的载荷是否齐全、在两道硬闸和 4 道确认闸（你拍板）前停下。**判断力在岗位 skill 里，节奏在 `b2b-run` 里。**

和 PM 的分工：`b2b-project-manager` 决定「做什么、怎么问你、怎么验收」，`b2b-run` 决定「按什么顺序跑、谁读谁写、什么时候停」。前者对你，后者对文件，不重叠。

路径约定写在 `b2b-run` 里：skill 根目录是本仓库的 `skills/`（随安装位置变化，只读）；项目产出写在**当前工作目录**（VS Code 里打开的那个建站项目文件夹）下，全部相对路径，运行状态只看该目录下的 `./_内部/RUN.md`。任何项目文件都不进 `skills/`。

## 流水线

参与的 agent（顺序）：PM → 研究员 → 策划 → 文案 → 设计 → 前端 + 后端 → SEO → 测试 → PM 验收 → 增长运营（3–6 个月）

## 四道闸（确认闸，你拍板）

| 闸 | 你看什么 | 这一步只定什么 | 过了触发什么 |
|---|---|---|---|
| G1 结构 | 站点地图 + 首页逐屏线框 | 页面、顺序、首屏放什么 | 文案与设计开工 |
| **G2 方向** | 视觉方向单（一页纸，不是页面） | 配色、字体、气质 | 设计出首页 |
| G3 设计 | 首页桌面 + 手机 + 一个内页 | 版式、层级、区块排布 | 前端开工 |
| G4 验收 | 测试站全站 | 事实错误与缺陷 | 上线交接：验收单你逐项打勾，留下资产清单与后台手册 |

文案不单独设闸：你只核事实来源表的中文事实列，不阻塞下游。

**过闸即冻结**——每道闸只收自己层级的意见。过了闸再回头改上一层 = 返工：agent 要提醒代价（下游哪些产出要重做），但要不要返工由你决定。

完整规则（什么算返工、怎么冻结）在 `b2b-project-manager/references/确认与改稿规则.md`，每道闸都要在 `_内部/确认记录.md` 留一行。

## 第三方参考数据

部分 reference 的数据改编自开源项目 ui-ux-pro-max（MIT）。出处、采用范围、以及**刻意没采用的部分和原因**记在 `NOTICE.md`。改编文件头部的出处行不要删——MIT 要求再分发时保留声明，而 reference 是会随仓库和项目文件一起流出去的。

## 岗位 agent 契约

每个 skill 的「流水线接口」开头都有一行压缩版，这里是完整版。四条都是硬的。

**一、只收自己的输入文件，收不到上游的完整对话。** agent 拿到的是文件，不是别的 agent 跟你聊了什么。这条决定了上游必须把结论写进文件——写在对话里、口头交代的东西，下游看不见，等于没交接。

**二、只写自己的输出文件，不改别人的产出。** 前端觉得文案太长，不能自己改文案；设计觉得线框不对，不能自己改线框。只能回流。这条是防止同一份产出有两个作者，改到最后没人知道哪版是准的。

**三、不各自问你。** 所有要你补的东西追加到 `_内部/待用户决定.md`，经 PM 汇总，一次问完，一次最多 5 条，每条带默认值。下游 agent 各自来问你，是你的时间被耗光的最快方式。

**四、不横向调用其他岗位 agent。** 发现上游缺口，按「回流」写一份回执交给 PM，由 PM 调度谁来修。agent 之间不互相指挥。

## 回流原则

任何 agent 发现上游缺口，回到对应上游 agent 修正，不各自绕过；需要你补充的一律经 PM 汇总后一次问你。结构性问题（导航、页面、区块）回策划；事实回 PM；措辞回文案；视觉回设计；DOM / 性能回前端；链路 / 基础设施回后端；收录回 SEO。

回流不是甩锅：回执必须写清楚具体位置、期望结果、以及至少一个可选替代方案，只说「做不了」「排不下」「没效果」的回执，对方可以直接退回。

## 交接载荷

每个 skill 的「流水线接口」里有一节「交接载荷」，写明每条交接必须随行的字段。**缺项即视为未交接，下游可以直接退回，不必勉强开工。**文件名不是契约，字段才是——一份缺关键词表的研究简报，和没交是一回事。

## 文件契约

每份文件的唯一合法名字和落盘目录在 `文件契约.md`。各 skill 的输入 / 输出、交接载荷、`b2b-run` 的目录树都从那里抄。执行器按路径找文件，名字不一致等于文件不存在——这一轮审计查出七处 `.csv` / `.md` 与漏列的不一致，就是没有这张表造成的。

## 职责边界

谁拥有哪项职责，见 `职责归属矩阵.md`。那张表是三样东西的共同依据：每个 skill 的 description 结尾的否定边界、交接载荷的方向、以及回流的去处。改那张表就要同步改这三处，否则会出现两个 skill 都认领同一件事、或者都不认领。

## 特殊情况的共同原则

每个 skill 都有一节「特殊情况处理」，按岗位写具体动作；下面是所有岗位共用的底线，冲突时以这里为准。

1. **不编造**：没有的数字、证书、买家名、图，一律不写不放；用 `[待确认：X]` 占位并进待确认清单；上线前占位必须清零（测试记 P1）。证明不了的宣称换成可证明的相邻表述，你坚持要用的话由你在确认记录里拍板并承担。
2. **不用网图、不冒充**：产品位与车间位只用实拍或统一风格的示意图 / CAD / 界面截图；授权图库图只做背景与行业氛围并加遮罩，不出现在 Our factory / Our products 语境；贸易公司不写 Our factory。
3. **默认推进，不停工等你**：资料不全时按行业默认值 + 假设清单推进（策划的初判 1 小时内出）；需要你补的问题经 PM 汇总一次问，每次不超过 5 条，每条带默认值；你一时定不下来就按默认推进并记假设；下游 agent 不各自问你。
4. **素材缺口三级过渡**：你自己用手机拍（给 10 张最小素材包清单和拍摄指南；拍不了就请本地摄影半天）→ 示意图 / CAD 渲染 / 界面截图 / 图标 + 参数卡 → 授权图库仅做氛围。设计与前端都预留“图到位后升级版”：组件位置不变，换图即可。
5. **风格随素材降级**：没图只能选国际企业风、工业硬核风、Bento 排版型；极简、摄影驱动、暗色高级科技必须有专业图。
6. **证据不足就降级结论**：测试在事实未确认、素材占位、公司收件邮箱未验证时最高只给“修复后可上线”；P0 / P1 不因时间压力让步。
7. **基础设施缺口有兜底路径**：没企业邮箱用 Zoho / 阿里免费企业邮或事务邮件服务；没域名就新注册，注册在公司自己名下；域名在前服务商手里 15 天拿不回就新注册并后续 301；没 WhatsApp 先隐藏按钮不放空号。
8. **目标市场主导**：你现有资料或旧站面向国内（中文站、“企业文化 / 荣誉资质 / 新闻动态”栏目、大红大黄满屏、弹窗客服、领导视察照）时，结构、视觉、叙事一律按出海目标市场重来，国内资料只作事实来源，不做“翻译版”；研究员出一张国内站 vs 本土同行的差异对照表作为依据；没有明确目标市场按英文国际站默认（国际企业风、欧美密度）。

## 每个 skill 的共同骨架

岗位定位与上下游 → 你在这个环节会提什么需求 / 背后意图 / 怎么满足 / 归因（业务逻辑、交互体验、视觉层级、技术与性能、风险）→ 工作流程 → 决策归因示例 → 输出格式 → 交接与验收标准 → 流水线接口（契约 → 输入 → 输出 → 交接载荷 → 完成判定 → 回流）→ 特殊情况处理 → 常见错误。

description 的写法也统一：正向写「这个岗位干什么 + 什么时候用」，结尾必须有一句「不负责 X（归 Y）」，点名兄弟 skill。路由靠的就是这一句，没有它，撞车的触发词会让两个 skill 同时被唤起。
