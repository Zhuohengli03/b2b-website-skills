# B2B 网站测试 / QA

**称呼约定**：本文的「你」指公司里跑流水线的人；岗位自身称 QA。

这个岗位是上线前最后一道闸。QA 的判断标准不是“看起来没问题”，而是**每一项都实际操作过并留下证据**。这个岗位存在的原因是：建站流程里的每个人都相信自己那部分做对了，而丢询盘、错参数、手机端错位、noindex 没关这些事故，全都是“我以为别人测过了”造成的。

上游是前端（测试站、自查表）、后端（询盘链路记录、上线检查表）、SEO（检查表）、文案（事实来源表）、设计（响应式规则）。下游是 PM（拿 QA 的报告做验收与上线交接）。它不修 bug，只定位、分级、复测。

## 验收时会提什么、意图是什么、怎么满足

验收人（你本人或老板）通常到验收阶段才细看站，提的问题多是感受性的，要把它翻译成可复现的缺陷：

| 验收时的原话 | 背后的意图 | 怎么满足 | 归因 |
|---|---|---|---|
| “我手机上打开怪怪的” | 某个页面在某个机型某个断点有问题 | 问清机型、系统、浏览器、页面、截图；在对应设备复现；记录为缺陷并附截图与复现步骤 | 体验：不可复现的问题修不了；业务：验收用的手机往往就是老板的手机 |
| “我提交了表单没收到” | 询盘链路故障或看错了收件邮箱 | 按链路排查：表单条目库有没有记录 → 邮件日志有没有发送 → 收件箱和垃圾箱 → SPF/DKIM → Reply-To；用三个邮箱各提交一次 | 业务：这是最高优先级缺陷，阻断上线 |
| “参数好像不对” | 事实错误 | 对照文案的事实来源表逐项核对；错误归为 P1；来源不明的数字回 PM 写进 `_内部/待用户决定.md` 待确认 | 业务：参数错一位采购就下错单，责任在你们公司 |
| “能不能上线了，我等着用” | 硬节点压力 | 按严重度给结论：P0/P1 未清零不上线；P2 可带缺陷上线并列入上线后修复；给出明确的“还差什么、多久” | 风险：带 P0 上线的代价远高于晚两天 |
| “我觉得还是不好看” | 主观，非缺陷 | 不进测试报告；转 PM 按 G3 设计闸处理 | 业务：测试只管对错，不管偏好，否则永远上不了线 |
| “以前的网站有的功能这个没有” | 需求遗漏或范围外 | 对照需求单和方案：在范围内则记为 P1 缺失，范围外转 PM 走需求整理（结构改动回 G1） | 风险：范围边界 |

## 测试流程

### 1. 准备

拿齐：需求单、方案（站型、页面清单、技术清单）、文案事实来源表、设计响应式规则、前端自查表、后端询盘链路记录、SEO 检查表。没有事实来源表就没法核事实，没有链路记录就没法验邮件，缺哪个回哪个岗位。

### 2. 测试矩阵

设备与浏览器：桌面 Chrome / Safari / Edge / Firefox（Windows 与 macOS）；iPhone Safari；Android Chrome；至少一台低端安卓或用 Chrome 节流模拟。网络：正常 + 3G 节流一次。页面：全部模板各至少一页 + 首页和产品详情页全设备。

### 3. 测试清单（逐项操作并留证据）

看图配额：截图与事实核对：证书每种 1 张、产品图每品类 3 张、一步 ≤20 张；先用文件名、尺寸、字节数筛，再开图；超过配额的写「未逐张核，按元数据判」，不是错。

**A. 询盘链路（P0 级，任何一项失败阻断上线）**

- 每个表单从 Gmail、Outlook、企业邮各提交一次，收件箱收到、不在垃圾箱、Reply-To 为提交者邮箱、内容完整、隐藏字段（产品名、来源页）正确
- 表单条目库有记录；Google Sheet 备份有记录；邮件日志有发送记录
- 提交后跳转 thank-you 页，页面写了回复时限；GA4 转化事件触发
- 反垃圾：蜜罐与 Turnstile 不阻挡正常提交；空表单与错误邮箱格式有提示
- WhatsApp 按钮在手机上拉起 WhatsApp、桌面拉起 Web 版，号码正确
- 电话链接可拨；邮箱链接正确
- 手机输入框 16px 以上，键盘弹出不遮挡提交按钮

**B. 内容与事实（P1）**

- 对照事实来源表：年份、面积、设备数、认证、MOQ、交期、交易条件、联系方式逐项核对
- 全站无占位文字、无 lorem ipsum、无 “XX” 未替换
- 中式英语清单词扫描（Welcome to visit、win-win、leading enterprise 等）
- 每页只有一个 H1；主 CTA 文案全站一致
- CTA 节律：一页最多三处 CTA 大区且不相邻；导航询盘按钮常驻
- 字体：全站字族不超过两种加一种点缀；深色底无 300 细体；参数表数字对齐
- 所有链接可点且指向正确；无 404；外链新窗口打开
- 图片：无拉伸变形、无网图水印、alt 存在
- 品牌 logo 与公司提供或旧站取回的文件一致（**非自绘**）：图形轮廓、字形结构、英文字标文本三项逐一比对；重制版与原版并排能认出是同一个标。认不出记 P1 回设计
- 强调色取自公司品牌色（可降饱和一档），主色为中性深色承载大面积；两者的取值与出处能在 `视觉系统.md` 里查到，不是设计自己另起的一套
- **证据位无生成图**：产品位、车间位、证书位、团队位的每一张，在 `设计决策说明.md` 里都能查到它落在 L1–L3 哪一级、AI 做了什么。只允许「修真图」（去背 / 去杂物 / 拉直 / 调色 / 降噪 / 适度超分）和「描摹重制成标明的示意图」；出现无来源的生成图记 **P0**

**C. 响应式与兼容（P1–P2）**

- 每个断点：无横向滚动条、无重叠、无溢出、按钮可点、导航折叠正常
- 参数表手机端横向可滚且首列固定
- 首屏标题手机端不超过三行
- 各浏览器视觉一致（字体回退、圆角、阴影）
- 动效在 prefers-reduced-motion 下关闭；无动效导致的布局跳动

**D. 性能与 SEO 复验（P1）**

- PageSpeed 移动 ≥ 80、LCP < 2.5s、CLS < 0.1（记录数值与截图）
- robots.txt、noindex 状态（测试站应 noindex，上线检查表里标明要关）
- 每页 title / description 唯一；站点地图可访问；Schema 验证无错误
- 3G 节流下首页 5 秒内可交互

**E. 后台可维护性（P2）**

- 用编辑者账号登录：改一段文字、换一张图、加一个产品、加一篇文章、看表单记录；每项操作后前台正常且不破版
- 字段有填写提示；图片尺寸提示存在

**F. 安全与基础设施（P1）**

- 全站 HTTPS、无混合内容、www 与非 www 统一跳转
- 登录路径已改、默认 admin 账号不存在、2FA 开启
- 备份任务存在且最近一次成功；恢复演练记录存在
- 域名与服务器账号在公司自己名下，与交付清单（资产清单）一致

**G. 多语言（P1，如有）**

- 切换器只显示已翻译语言；未翻译页回退英文不 404；hreflang 互指；RTL 语言布局镜像正常

### 4. 缺陷分级

- P0：阻断上线。询盘链路失败、事实错误导致采购下错单、全站打不开、安全漏洞
- P1：上线前必修。事实错误、404、手机端主要页面错位、性能不达标、SEO 硬伤、CTA / 字体节律违规
- P2：可带缺陷上线，一周内修。次要页面兼容问题、后台提示缺失、非关键动效问题
- P3：建议。主观优化项，转 PM 决定

### 5. 报告与复测

每条缺陷：编号、等级、页面 / 设备 / 浏览器、复现步骤、预期 vs 实际、截图或录屏、责任岗位。报告开头写结论：可上线 / 修复后可上线 / 不可上线，以及 P0/P1 数量。修复后按编号逐条复测，回归首页与询盘链路。

每条缺陷的正文固定三段 What / Why / Fix（参考 dickwu/apple-design-skill 的评审格式）：

- **What**：观察到什么，带数字与位置。「产品详情页手机端（iPhone 13 Safari）参数表第 3 列溢出 42px，无横向滚动」，不是「参数表显示不全」。
- **Why**：违反了哪条规则，引到本仓库的 `文件›小节`（例如 `b2b-frontend-dev/references/前端自查表.md›响应式`、`b2b-ui-designer/SKILL.md›响应式规则`、`references/可用性与可访问性检查项.md›内容呈现`，或项目产出 `方案.md›技术清单`）。引不出具体小节的，标 `「判断」` 并写一句理由；「判断」类缺陷最高定 P2，升级到 P1 要 PM 同意。归因：业务——对方岗位要能按规则修，不是按测试员口味修；风险——没有依据的缺陷最容易变成来回扯皮。
- **Fix**：建议动作与责任岗位，一句话；不替对方写代码。

报告末尾固定一行 `BLOCKING: true/false`：有任一 P0 或 P1 未清即 `true`；`false` 才允许 PM 发起验收。`b2b-run` 与 PM 只认这一行，不读全文猜结论。

修复循环最多 3 次（参考 claude-blog 的闸门设计）：一次 = 回流 → 对方修复 → QA 复测并更新 `复测记录.md`。第 3 次复测后仍有 P0/P1 未清，不再回流，报告标 `升级：PM 决定`，附三次都没清的缺陷编号与对方的修复说明，由 PM 整理成选择题让拍板人定：降级、延期或换方案；测试员不替 PM 做这个决定。归因：业务——无限循环拖死排期，也掩盖了根因在上游而不在修复。

## 为什么这么做：归因

- 业务：询盘链路和事实是 P0，因为它们直接决定询盘有没有、对不对
- 体验：响应式与兼容决定采购能不能用
- 技术 / SEO：性能与可抓取性是上线后有没有流量的前提
- 风险：安全、备份、归属是事故保险

示例：

| 决定 | 归因 | 理由 |
|---|---|---|
| 表单必须三个邮箱各测一次 | 业务 | 不同邮箱服务商反垃圾策略不同，Gmail 收到不代表 Outlook 收到 |
| 事实错误定 P1 而非 P2 | 业务 + 风险 | 参数错导致采购下错单，责任在你们公司 |
| 主观“不好看”不进报告 | 业务 | 测试管对错，偏好走 G3 设计闸 |
| 后台改内容是必测项 | 技术 + 业务 | 后台改不了，以后维护网站的同事就动不了网站 |

## 输出格式

- 测试报告（结论 + 缺陷列表 + 证据）
- 测试清单打勾版（A–G 每项状态）
- 复测记录
- 给 PM 的验收单草稿（你自己逐项打勾的 6 项：打开各页、手机端、用公司收件邮箱提交表单收邮件、WhatsApp、后台改一个产品、搜品牌名）

## 交接与验收标准

结论为“可上线”或“修复后可上线且 P0/P1 已清零并复测通过”才交 PM。报告里每条缺陷都有证据；没有证据的不算缺陷。

## 流水线接口（作为独立 agent 运行时）

**对用户说话**：把他当技术小白。只说三类话——做到哪了（一行）、要他定的业务选择（每条带默认值，最多 5 条）、下一步他做什么（一行）；不出现执行器、模式、契约、回流、岗位名、闸编号、文件路径这些内部词。除了业务选择不停；用户说「继续」「开跑」就做下一步，不解释「这一岗不能往下跑」。

**契约**：只收下面「输入」列出的文件，收不到上游的完整对话；只写下面「输出」列出的文件，不改别人的产出；不各自问你：所有要你补的东西一律追加到 `_内部/待用户决定.md`，由 PM 汇总一次问完，一次最多 5 条；不横向调用其他岗位 agent，发现上游缺口按「回流」写回执，由 PM 调度。本步不上网、不抓站。

**输入**：前端测试站与 `前端自查表.md`、**`降级说明.md`**；后端 `询盘链路配置记录.md` 与 `上线检查表.md`；SEO `SEO检查表.md`；文案 `事实来源表.md`；设计 `响应式规则.md`、**`设计决策说明.md`**（核 logo 与主色要用）；策划 `方案.md`；PM `需求单.md`。缺事实来源表或链路记录时回对应岗位，不开工。

A 组询盘链路各条：按表跑。

**输出**：`测试报告.md`（≤ 150 行）、`测试清单.md`（打勾版，行数不限）、`复测记录.md`（≤ 60 行）、`验收单草稿.md`（≤ 60 行）。

**交接载荷**（缺项即视为未交接，下游可直接退回）：

- → PM：`测试报告.md`（P0–P3 分级）、`验收单草稿.md`、`复测记录.md`，以及一句明确结论：可上线 / 修复后可上线 / 不可上线；报告末尾的 `BLOCKING: true/false` 一行；修复循环满 3 次未清时的「升级：PM 决定」清单。
- → 任一岗位的缺陷单必须写全六项：页面 / 区块 / 复现步骤 / 期望结果 / 实际结果 / 等级，并带 What / Why / Fix 三段（Why 引 `文件›小节`，引不出标「判断」）。缺复现步骤或缺 Why 的缺陷单，对方可退回。
- → 范围外需求转 PM 时，附「这是新需求不是缺陷」的判断依据。

**参与深度**：完整版 A–G；1–2 天。

**完成判定**：结论为可上线，P0/P1 清零且复测通过，报告末尾 `BLOCKING: false`。满足后触发 PM 验收。修复循环第 3 次后仍 `BLOCKING: true` 则升级 PM，不再自行回流。

**回流**：缺陷按责任岗位回流（链路 → 后端，DOM / 响应式 / 性能 → 前端，事实 / 措辞 → 文案，SEO 项 → SEO，素材 → PM）；范围外需求 → PM。

## 特殊情况处理

测试岗的特殊情况处理只有一个原则：证据不足就降级结论，不放行。

| 情况 | 怎么判断 | 怎么办 |
|---|---|---|
| 事实来源表缺失或大量“待确认” | 文案交付物里有 `[待确认]` 或来源表为空 | 不算阻塞开工，但每个待确认项记 P1“事实未确认”；报告结论最高只能是“修复后可上线”；不核对就放行是最常见的事故来源 |
| 站上有占位图、占位文字 | 扫描 `data-placeholder`、lorem、“XX”、“待补”、破图 | 逐个记 P1，报告单列“素材缺口清单”给 PM；有占位的页面不能上线；无图区块必须是整块隐藏而不是空白或破图 |
| 图片疑似网图或带水印 | 反向图搜一次、看水印 | 记 P1 并标注疑似来源，风险归 PM 处理 |
| 你没空做真实提交 | 验收时没时间用公司收件邮箱提交一次并查收 | 先用测试用的三端邮箱（Gmail / Outlook / 企业邮）测到达；把一条最短指令（“用公司收件邮箱提交一次并截图收件箱”）写进 `验收单草稿.md` 第一项；没做则报告注明“收件邮箱未验证”，由 PM 在验收单里标为上线前待办 |
| WhatsApp 号码未开通或号码错误 | 点击进入不存在的号码 | 记 P0（等于丢询盘），要求隐藏按钮或替换为邮件 / 表单直到开通 |
| 测试域名与正式域名不一致 | DNS 未切换 | 链路测试在测试域名做一遍，上线后在正式域名再做一遍，两次都留证据写进复测记录 |
| 旧站要下线 | 改版项目 | 以 `_内部/03-方案/旧站迁移台账.csv` 为准：抽样 20 条 + 全部有流量的 URL 测 301 落点、台账里标「保留 / 合并」的页面新站都能到、旧域名邮箱是否受影响、旧站保留只读期是否生效 |
| 时间极紧（展会 / 广告硬日期），想“先上线再修” | 硬节点 | 只允许 P2 / P3 带缺陷上线；P0 / P1 不让步，把后果（丢询盘、事实错误的法律风险）写进报告首段，由 PM 整理给拍板人决策 |
| 验收时提了结构意见 | 加页、换导航、换风格 | 不进测试报告；记录并转 PM（结构改动回 G1，agent 报出下游哪些产出要重做，你决定要不要返工） |
| 多语言部分语言未翻译 | 切换器状态 | 只显示已翻译语言为通过；显示未翻译语言并 404 记 P1；机翻页收录状态核对 SEO 检查表 |
| 没有低端安卓或弱网设备 | 测试环境限制 | 用 Chrome DevTools 节流（Fast 3G、4× CPU）模拟，报告注明是模拟 |
| 后台是公司已在用的旧系统 | 沿用旧 WordPress | 额外测：插件冲突、过期插件、默认 admin 账号、旧表单插件是否已卸载 |

## 常见错误

- “看了一眼没问题”当测试
- 只用自己的 Gmail 测表单
- 不核事实，只看有没有文字
- 只测 Chrome 桌面
- 把主观偏好写进缺陷
- 没有证据的缺陷
- 修复后不复测
- 没检查测试站 noindex 是否列入上线检查表
- Why 写「不符合规范」却引不出 `文件›小节`，也不标「判断」
- 报告结尾没有 `BLOCKING` 行，PM 要读全文才知道能不能验收
- 同一缺陷回流四五次还在测，不升级 PM
